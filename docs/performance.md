# 性能与资源预算（为什么这套后端能跑在小机器上）

这套自建后端的目标不是「功能对齐 Emby」，而是**在 1~2 核、1~2G 内存的机器上稳定出流**：
扫描不把内存吃满、不把磁盘喂满 fsync、刮削不逐条串行等网络。

数字口径以 `scripts/smoke_test_scan_budget.py` 为准（CI 每次都会跑），
下面引用的是 162 个文件（150 部电影 + 2 部剧 12 集）的实测值。

## 一、扫描

| 维度 | 旧实现 | 现在 | 说明 |
| --- | --- | --- | --- |
| 条目查询 | 每个文件 1~3 次（条目 / 剧集 / 季） | 每 `SCAN_BATCH` 个文件一次 | 十万文件：几十万次 → 几百次 |
| 提交（fsync） | 每个文件一次 | 每批一次 | 实测 166 → 5 次；这是「扫一次库把盘拖住」的主因 |
| 探测（ffprobe） | 串行，单文件最长 90 秒超时 | `SCAN_WORKERS` 并行 | 一个坏文件不再拖死整库进度 |
| TMDB 刮削 | 逐条串行等网络 | 同一条目内串行、条目之间并行 | 搜索 → 详情有依赖，所以放在同一个工作线程里 |
| TMDB 调用数 | 每条 1~2 次，无缓存 | 预热与写库共用一份响应缓存 | 不会因为「预热 + 写库各调一次」双倍耗配额 |
| 目录列举 | 每个文件两次（找图 + 找字幕） | 每个目录一次 | 远程挂载上等于每次少两次网络请求 |
| 内存 | 清理阶段把整库条目一次载入 | 分批处理，会话不堆积对象 | 大库不再出现内存尖峰 |

可调环境变量：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `SCAN_BATCH` | `400` | 每批文件数（批量查库 / 落盘的粒度）。小内存机器可以调小，比如 `100` |
| `SCAN_WORKERS` | `4` | 并行 IO 线程数（探测 / 目录 / TMDB）。核数少就调小，`1` 表示退回串行 |
| `TMDB_API_KEYS` | — | 多密钥轮询（`key1,key2`），一个 key 限额后自动换下一个 |

## 二、播放

- **直连优先**：能满足客户端（容器/编码/码率）就 `FileResponse` 直出，用 `Range` 支持拖动；
  只有确实不兼容才起转码，转码是**子进程**，进程退出即回收，不在主进程里堆帧。
- **会话在内存**：播放会话不写热点表，避免每次心跳都产生写入放大。
- **图片代理**：远程海报走服务端代理 + 客户端缓存头，避免每个客户端各自去撞 TMDB。

## 三、已知瓶颈（按收益排序的下一步）

1. **逐集查剧集/季**：剧集层级（episode → season → series）仍在写库线程里按集查两次。
   电影库无感，剧集库（十万集）会明显。修法是把批内已加载/已创建的剧集与季放进一张批级映射，
   由批次预取统一填好（数据结构预留了 `_Pending.series_guid/season_guid`）。
2. **清理阶段的候选集合**：删文件后的对账目前仍会遍历该库全部条目（已按批流式，但仍是全量）。
   可以做「目录 → guid」快照，只比对这个目录。
3. **增量扫描**：用目录的 `mtime` + 文件数做指纹，未变动的目录整目录跳过（对追新场景是最大的一步）；
   配套可以做「按 mtime 倒序扫描」，让新入库的片子最先出现在客户端。
4. **远程挂载目录列举**：现在只在扫描器内部缓存，未落到 provider 层；播放路径上的重复列举还能再省。
5. **刮削图片本地化**：把海报/剧照抓一份到本地磁盘（或对象存储），播放高峰不再依赖 TMDB。
6. **扫描限速**：给扫描线程加 `nice` / IO 优先级，避免扫描期间影响正在播放的用户（播放进程优先）。

## 四、怎么验证

```bash
# 资源行为（批次化 / 并行 / 缓存 / 清理），CI 会跑
python scripts/smoke_test_scan_budget.py

# 功能正确性
python scripts/smoke_test_emby.py       # 扫描 + 协议面端到端
python scripts/smoke_test_mounts.py     # 本机路径 / local / strm / 远程挂载 / 多来源
python scripts/smoke_test_media_search.py
```

`smoke_test_scan_budget.py` 会打印实测数字（查询数、条目表 SELECT 数、提交数、
探测与刮削的峰值并发、TMDB 调用数、`os.listdir` 次数、Python 峰值内存），
做性能改动时先看这张表，别只看耗时。
