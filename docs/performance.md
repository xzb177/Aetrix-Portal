# 性能与资源预算（为什么这套后端能跑在小机器上）

这套自建后端的目标不是「功能对齐 Emby」，而是**在 1~2 核、1~2G 内存的机器上稳定出流**：
扫描不把内存吃满、不把磁盘喂满 fsync、刮削不逐条串行等网络。

数字口径以 `scripts/smoke_test_scan_budget.py` 为准（CI 每次都会跑），
下面引用的是 162 个文件（150 部电影 + 2 部剧 12 集）的实测值。

## 一、扫描

| 维度 | 旧实现 | 现在 | 说明 |
| --- | --- | --- | --- |
| 条目查询 | 每个文件 1~3 次（条目 / 剧集 / 季） | 每 `SCAN_BATCH` 个文件一次 | 十万文件：几十万次 → 几百次 |
| 提交（fsync） | 每个文件一次 | 每批一次 | 实测 166 → 5 次；这是「扫一次库把盘拖住」的主因 |
| 探测（ffprobe） | 串行，单文件最长 90 秒超时 | `SCAN_WORKERS` 并行 | 一个坏文件不再拖死整库进度 |
| TMDB 刮削 | 逐条串行等网络 | 同一条目内串行、条目之间并行 | 搜索 → 详情有依赖，所以放在同一个工作线程里 |
| TMDB 调用数 | 每条 1~2 次，无缓存 | 预热与写库共用一份响应缓存 | 不会因为「预热 + 写库各调一次」双倍耗配额 |
| 目录列举 | 每个文件两次（找图 + 找字幕） | 每个目录一次 | 远程挂载上等于每次少两次网络请求 |
| 内存 | 清理阶段把整库条目一次载入 | 游标分批（每批 `SCAN_BATCH`） | 十万级库不再出现内存尖峰 |
| 清理的从属数据 | 删条目时只删条目本身 | 同时清掉媒体流与播放进度/收藏 | 播放进度没有 ORM 级联，旧实现会留下只增不减的孤儿行 |
| 重扫（追新） | 每个文件走完整流程（~4 条 SQL + 1 次提交） | 目录指纹未变就整个跳过 | 2000 文件库：2455 ms → **144 ms**（见「三、已知瓶颈」） |
| 清理候选集 | 遍历该库全部条目 | 先两次计数证明无需清理，退回遍历时每批 5000 条只读 4 列 | 十万条目：2097 ms → **37 ms** |
| 探测子进程优先级 | 与 API 同优先级，和播放抢 CPU/磁盘 | `SCAN_IO_NICE` 只降 ffprobe 子进程 | `nice` 是进程级的，本进程不能降（会连播放一起降） |

可调环境变量：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `SCAN_BATCH` | `400` | 每批文件数（批量查库 / 落盘的粒度）。小内存机器可以调小，比如 `100` |
| `SCAN_WORKERS` | `4` | 并行 IO 线程数（探测 / 目录 / TMDB）。核数少就调小，`1` 表示退回串行 |
| `TMDB_API_KEYS` | — | 多密钥轮询（`key1,key2`），一个 key 限额后自动换下一个 |
| `SCAN_INCREMENTAL` | `1` | 目录指纹增量扫描（置 `0` 回到「每次全量处理」的旧行为） |
| `SCAN_CLEANUP_BATCH` | `5000` | 清理阶段每批读多少条目（不碰 IO，批越大越省往返） |
| `SCAN_IO_NICE` | `10` | 探测子进程的 niceness（`0` 关闭）；有 `ionice` 时同时降 IO 优先级 |

## 二、播放

- **直连优先**：能满足客户端（容器/编码/码率）就 `FileResponse` 直出，用 `Range` 支持拖动；
  只有确实不兼容才起转码，转码是**子进程**，进程退出即回收，不在主进程里堆帧。
- **会话在内存**：播放会话不写热点表，避免每次心跳都产生写入放大。
- **图片本地化**（v2.17.0）：刮削到的海报/背景图落一份到 `EMBY_IMAGE_DIR`，客户端从本服务器
  拿图；缓存被清掉会按需自愈，落不下来退回代理 —— 源站慢/不可达时媒体库封面不再跟着抖。
- **挂载目录列举缓存**（v2.17.0）：`MOUNT_LIST_CACHE_SECONDS`（默认 5 秒）内同一目录只问一次
  网盘，扫描与播放共用；失败不缓存、同一目录单飞、内存有上限（`MOUNT_LIST_CACHE_MAX`）。

## 二·五、协议路由的线程模型（v2.13.0）

- **按关注点拆分模块**：协议面原先集中在 `backend/emby_server/api.py`（2100+ 行），现拆成
  `api.py`（系统信息 / 认证 / 列表与详情 / 播放核心）、`media_routes.py`（图片 / 下载 / `hls1`）、
  `compat_routes.py`（会话上报与协议补齐）、`stream_routes.py`（容器变体流 / 原始文件 / 字幕）。
  四个模块把路由注册到**同一个** `emby_router` 上，导入顺序与拆分前的定义顺序逐条一致，
  所以 `mount_routes` / `image_routes` / `session_routes` 的「路径 + 端点名替换」照旧生效。
- **同步 `def` 优先**：路由体内没有 `await` 的一律写成同步 `def`，由 Starlette 线程池执行——
  同步 SQLAlchemy 查询、读盘、远程代理都不会占住事件循环。只有真正需要 `await` 的才写
  `async def`：要 `await request.json()`、`await` 异步响应流（`video_stream` / `video_hls`），
  或者被别的模块 `await` 复用。新加端点时按这个口径选签名。
- **为什么要拆**：文件小，单次改动的 diff 可读、可评审；后续把剩下的异步路由换异步 ORM
  或继续下沉阻塞调用时，改动面是可控的。
- **慢动作必须有 `*_async` 变体**（v2.20.2）：确实需要 `await` 的端点里也不能直接调阻塞函数。
  典型例子是「停止转码」：`stop_transcode()` 要 `terminate` 子进程、等它退出（最多 5 秒）、
  再递归删掉整场播放的分片目录，一次「结束播放」就能把整个进程按住。现在事件循环上一律用
  `stop_transcode_async()` / `stop_transcodes_for_async()` / `stop_all_transcodes_async()`
  （阻塞部分 `asyncio.to_thread`，全部会话并发停），同步版本只留给同步路由与后台线程
  （维护周期、`_reap_in_background`）。`scripts/smoke_test_transcode_stop.py` 用后台心跳
  量出差别（同步基线 0.61s 空洞 vs 异步 0.01s），并静态拦住「`async def` 里调同步实现」的写法。
- **停止转码按「用户 + 条目 guid」反查**：转码会话 id 是 `start_transcode` 生成的 uuid
  （只出现在 HLS 播放列表的 `?session=` 上），与客户端的 `PlaySessionId`（播放会话键）
  不是同一个值；`stop_transcode(session_key)` 这种写法永远匹配不上、等于什么都没停到。

## 二·六、分类筛选的索引（v2.15.0）

分类值（流派 / 工作室 / 标签 / 发行平台）原先只存在 `emby_items` 的逗号分隔文本列里，
客户端点「类型 / 制作公司」时服务端只能写 `genres ILIKE '%动作%'` —— **前置通配符用不上任何索引**，
等于每次筛选都把整库扫一遍（代价随库大小**线性增长**）。现在由
`emby_item_facets(item_id, kind, value)` 承担：

| 环节 | 做法 |
| --- | --- |
| 写入 | 挂在 SQLAlchemy Session 的 `before_flush` / `after_flush` 上：同一事务里重建这些条目的关联行（先删后插）。扫描器、图片修复、将来任何写入路径都不用手动调；批量 Core 删除走不到事件，由 `prune_orphans` 兜底 |
| 查询 | `MediaItem.id IN (SELECT item_id FROM emby_item_facets WHERE kind=? AND value IN (...))`，走 `(kind, value, item_id)` **覆盖索引**；主查询按主键取条目，文本列上不再有 LIKE |
| 取值菜单 | 一次覆盖索引扫描拿全 kind 的取值（带进程内缓存），分级/年份改成单列 `DISTINCT` |
| 写入细节 | 新条目确实没有旧行，所以**只有分类值变过的老条目**才先删后插；扫描器每批都是新条目，热路径上省掉一次无谓的 DELETE |
| 老库 | 启动维护按 id 水位分批回填（每块提交，可断点继续）；筛选路径也带预算补块（5s 冷却）。**没补完就先退回旧匹配**，结果一样对，不会出现「升级后筛选空白」 |
| 语义 | 关联表侧是「全等，或取值里包含该名字（大小写不敏感）」，与旧 `ILIKE '%x%'` 一致（传 `Action` 照样命中 `Action-Adventure`） |

可调环境变量：`ITEM_FACETS_FILTER_BUDGET`（筛选路径一次补多少条，默认 2000）、
`ITEM_FACETS_BACKFILL_BATCH`（维护回填批大小，默认 2000）、
`ITEM_FACETS_CACHE_TTL`（取值缓存 TTL，默认 600s；扫描/回填会主动失效）。

### 实测数字（10 万条，SQLite，`scripts/benchmark_item_facets.py`）

这是**读多写少**的取舍：省在客户端反复点的读路径，付在条目变化时的写路径。
两头都量过，不要只记住结论：

| 项目 | 旧（逗号文本列） | 新（关联表 + 索引） | 说明 |
| --- | --- | --- | --- |
| 少见取值筛选（命中 20 条） | 19.9 ms | **0.06 ms** | 约 300x；耗时随**命中条数**走，与库总量无关 |
| 常见取值筛选（命中 29% 库） | 21.6 ms | 21.2 ms | **基本持平**：命中三万条时，索引也帮不上忙 |
| 筛选菜单取值 | 153.7 ms | **11.5 ms** | 13x（旧实现还把所有列读回来物化） |
| 扫描写入（ORM 新建 5000 条） | 775 ms | 842 ms | 每条多 13 µs（1.09x） |
| 看护周期 `prune_orphans`（36 万行、无孤儿） | — | 27 ms / 600s | 占 CPU 约 0.004% |
| 每次筛选的常数开销（`ensure_ready` + 取值匹配） | — | 0.8 ms | 取值 5000 个时 1.4 ms（纯内存比较） |
| 老库一次性回填 | — | 1.4 万条/秒 | 10 万条约 7 秒，分批提交、可断点继续 |

结论要诚实：**收益的大头不是「常见取值筛选」**（那本来就只是 20 ms 级的全表扫描），而是
筛选菜单（13x）、合成 Id 反查表（以前每个带 `GenreIds` 的列表请求都扫一遍库）与
**少见取值筛选（约 300x）**；而且旧口径的代价随库增长（50 万条时列表页约 107 ms），
新口径只随命中条数走。反过来，扫描入库多花 9% 的写时间——一次性成本，可以接受。

同一份基准还比过三种写法，**不要**随手改成「更直观」的那种：

| 写法 | 少见取值 | 常见取值 | 结论 |
| --- | --- | --- | --- |
| `id IN (子查询)`（当前实现） | 0.05 ms | 21.2 ms | 最好 |
| `JOIN` + `DISTINCT` | 0.06 ms | 23.2 ms | 常见取值更慢，且多值命中时要额外去重 |
| `EXISTS` 相关子查询 | 43.9 ms | 44.0 ms | 比旧的全表扫描还慢 2x，最差 |

重新量一遍：`python scripts/benchmark_item_facets.py [条目数]`（默认 10 万，只在临时库上跑，
不碰现有数据）。

### 性能护栏（CI 里跑，防止悄悄退化）

`python scripts/benchmark_item_facets.py --guard` 用 2 万条、几秒钟跑完，判定的是**比值**
而不是耗时（比值与机器快慢无关）。门禁的下限取得很保守——真实差距是阈值的几十倍，
只有真的改坏了才会红：

| 护栏 | 下限 / 上限 | 实测（本机） |
| --- | --- | --- |
| 少见取值筛选：关联表 / 全表 LIKE | ≥ 5x | 87x |
| 筛选菜单：覆盖索引 / 读整列 | ≥ 2x | 12x |
| 写入钩子开销（同一批 ORM 新建） | ≤ 3x | 1.15x |
| 看护周期 `prune_orphans` | ≤ 2000 ms | 5 ms |
| 每次筛选的常数开销（`ensure_ready` + 取值匹配） | ≤ 50 ms | 0.8 ms |
| 取值 5000 个时的名称匹配 | ≤ 20 ms | 1.4 ms |
| 回填吞吐 | ≥ 500 条/秒 | 1.4 万条/秒 |
| 两条路径的**条数**一致（常见 / 少见取值） | 相等 | 相等 |

这之前只有「功能正确」的门禁：把索引路径改回全表扫描、或者在写入钩子里塞逐条查询，
依赖都是绿的。

### 升级现场的四项演练（`scripts/smoke_test_item_facets_upgrade.py`）

关联表是**派生数据**，升级上来的老库在回填完成前会同时存在「索引路径」与「降级路径」。
这条测试专门演练开发机上很难自然遇到、但真实升级必经过的场景：

1. **降级口径**：还没回填完时筛选必须完全等于升级前的 `ILIKE '%x%'`（用冷却窗口把路径钉在降级分支上验证）；
2. **回填中途被打断**（进程被杀 / 写库报错）：异常向上冒、已提交的块保留、水位停在**块边界**，
   并且不会被误判成「已能代表全库」；
3. **重启续跑**：换个 Session 接着跑能补齐，幂等，关联行与条目列**逐行一致**（无重复、无遗漏、无孤儿）；
4. **读请求的补块**：一次请求把老库补完但每块不超过预算（实测每块 5/5/5/5/5/5/2 条），
   冷却窗口内的并发请求不重复抢写锁、也不改任何状态。

### 已做掉：增量扫描 / 清理候选集 / 挂载缓存 / 图片本地化 / 扫描限速（v2.17.0）

这一版把清单上剩下的五项一次做完，核心都是**别做白工**。

**① 增量扫描（目录指纹）**。重扫一个库时，绝大多数目录一个文件都没动过，但旧实现照样把每个
文件走一遍完整流程（找图片、找字幕、重建外挂字幕轨、每文件一次提交）。现在按目录记指纹：

| 目录形态 | 指纹 |
| --- | --- |
| 本机（含 local / strm 挂载） | `目录 mtime_ns : 目录项数` |
| 远程挂载（115 / WebDAV / AList / 云盘） | `目录项数 : 总字节数` |

指纹没变 → 该目录的文件**不做任何写库工作**，只把 guid 记进 `seen_guids`（否则清理阶段会把
它们当「文件已删除」）并确认库里那一行存在且不需要重探/重刮/补详情。任一条不满足就退回完整处理。
指纹变了 → 整个目录照常处理，处理完写回新指纹。

跳过**永远**以「库里那一行存在且不过期」为前提，指纹只决定「图片/字幕/轨道这些逐文件的重活
要不要重做」：指纹写早了、随后进程崩了也不会漏文件——下次扫描会因为「查不到那一行」而重新处理。
替换同名文件不一定动目录 mtime，所以跳过的前提里还要求「文件大小与库里的记录一致」。

实测（2000 个文件 / 40 个目录，本机库，`scripts/_tmp_*` 之外的等价脚本已固化成 CI 用例）：

| 场景 | 耗时 | SQL 条数 | 逐文件处理次数 |
| --- | --- | --- | --- |
| 冷扫（建库） | 2486 ms | 8075 | 2000 |
| 未变动重扫（旧） | 2455 ms | 8034 | 2000 |
| **未变动重扫（现在）** | **144 ms** | **29** | **0** |
| 追新（+1 个文件） | 136 ms | 138 | 1 个目录（51 次） |

也就是未变动重扫从冷扫的 95% 降到 **6%**，且新增内容立刻入库（只重做它所在的那个目录）。
`SCAN_INCREMENTAL=0` 可整体关掉回到旧行为。没配 TMDB 的部署同样吃到增量：
刮削不可能成功时不该因此让整库每轮重做（配好密钥后的下一次扫描自然会重新处理这些条目）。

**② 清理阶段的候选集**。稳定库真正要遍历的只剩「行已存在但库里没这一行」以外的情形——
老实现每次都对整库条目做 ORM 游标遍历。现在先用两次计数证明「没有可清理的条目」
（`_no_removals_possible`，已有），退回遍历时也改成**只取 4 个列的 Core 游标 + 每批 5000 条**：
十万条目的稳定库从 2097 ms 降到 **37 ms**（同库 `COUNT(*)` 3.6 ms）；真需要遍历时
2226 ms → **569 ms**。逐行删除依旧显式带上 `UserMediaData`（无级联），不留孤儿行。

**③ 远程挂载目录列举下沉到 provider 层**。扫描方向本来有「本次扫描内只列一次」的缓存，
而**播放方向完全裸奔**：`resolve_play_target` 每次请求新建提供者，实例级 cid/pickcode 缓存
对播放等于不存在——115 上放一个 `/电影/2024/x.mkv` 要重新逐级列目录。现在缓存下沉到
`mounts.cached_listing`（九个提供者全部套上，含 115 的 raw 列表）：

- 按「挂载 + 配置指纹 + 方法 + 目录」做 TTL 缓存（`MOUNT_LIST_CACHE_SECONDS`，默认 5 秒），
  扫描与播放**共用同一份**；返回拷贝（调用方会排序/裁剪），**失败不缓存**（网络抖动不被固化），
  同一目录**单飞**（并发只请求一次，锁是可重入的——子类实现可能套在另一个被缓存的列举上）；
- 扫描开始前 `clear_dir_cache()` 会连这份缓存一起清（扫描必须看当下的目录）；
- `MOUNT_LIST_CACHE_MAX` 给内存封顶（满了整体清空）。

实测（假提供者计数）：两次播放（各自新建提供者）从 4 次网盘列举降到 **2 次**；
播放侧 `exists` + `size` + `exists` 三个问句只列 **1 次**目录；远程库重扫每目录仍然只列一次
（指纹复用遍历用过的那一份，不额外打网络）。后台目录选择器走 `list_dir_uncached` 看当下。

**④ 刮削图片本地化**。封面原先只有 TMDB 远程地址，客户端每取一次图都要由服务器代理去第三方
拉一趟。现在刮削时把图落一份到本地（`EMBY_IMAGE_DIR`，默认 `<EMBY_TRANSCODE_DIR>/images`），
远程地址**始终保留**：

- 缓存文件被清掉（/tmp 重启清空、维护淘汰、换过海报）都能**自愈**——取图时发现本地不在就
  按需再落一份并记住路径；落不下来就退回原来的代理路径，行为与本地化之前一致；
- 本地化过的图（在缓存目录里）优先走本地；**用户自己放进媒体目录的封面不受影响**（仍按原顺序）；
- 内容寻址（同图只落一份）+ 按 URL 单飞 + 「临时文件 → fsync → os.replace」原子落盘；
- 维护周期回收没被任何条目引用的文件，并按 `EMBY_IMAGE_CACHE_MB`（默认 2GB）从旧到新淘汰；
  **有引用的图一张都不删**（宁可超上限并记日志），新增文件有保护期（`EMBY_IMAGE_GRACE_SECONDS`）。

**⑤ 扫描限速**。POSIX 的 `nice` 是**进程级**的，而扫描跑在 API 进程的后台线程里——直接给本进程
降优先级会把正在播放的请求一起降，那是错的。所以只降**子进程**：ffprobe 是扫描里唯一的外部进程，
既最吃 CPU、也最容易和播放抢磁盘 IO。`SCAN_IO_NICE`（默认 10，0 关闭）给探测子进程加
`nice -n N`，能用的系统上同时用 `ionice -c2 -n7` 把 IO 降到 best-effort 最低档。
只在启动时探一次工具可用性（`ionice` 存在但内核不允许时不能挡住 ffprobe）：实测子进程运行时
`os.nice(0) == 10`、`ionice -p` 报 `best-effort: prio 7`，包装后 stdout/退出码照旧透传。

### 已做掉：逐集查剧集/季（v2.16.0）

写库循环原来对**每一集**点查两次（先剧集、再季）。现在 `_prepare_and_prefetch` 在批次开头
把这一批用到的剧集与季一次查回（`guid IN (...)`），并按 guid 缓存到本次扫描结束
（`_ScanContext.series_items` / `season_items`，存对象而不是 id，因为循环后段还要用它们做
「集 → 季 → 剧」的海报回退）。十万集的老实现在二十万次往返上多花几秒；现在循环里
**一次按 guid 的点查都没有**（`smoke_test_scan_budget.py` 用 SQLAlchemy 的
`before_cursor_execute` 事件数出来断言 `guid 点查 = 0`）。

同一版还把这个 1651 行的文件拆出了两个模块，扫描器只剩遍历与写库：

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `scanner.py` | 1320（2.17.0 后约 1650，含增量扫描与指纹状态） | 文件遍历、解析、探测编排、写库、清理 |
| `tmdb.py` | 233 | TMDB 客户端（密钥轮询 + 短 TTL 缓存），与扫描状态无关 |
| `subtitle_match.py` | 166 | 外挂字幕的同名判定与语言识别（本机与远程挂载共用） |

`scanner.tmdb_client` / `scanner.match_subtitle_names` 等既有引用由 scanner 重新导出，调用方无需改动。

## 四、长期运行（跑几个月也不越跑越重）

扫描是「扫一次」的压力，长期运行还有另一类压力：**会随运行时间累积的东西**。
这些由 `backend/emby_server/maintenance.py`（看护线程）统一收尾，EM 与 EA 在启动时都会跑一遍，
之后每 `MAINTENANCE_INTERVAL` 秒（默认 600）跑一次：

| 会积累的东西 | 成因 | 收尾方式 |
| --- | --- | --- |
| `is_scanning` 停在 True | 进程被强杀（OOM / 重启 / kill -9），扫描标志来不及回写 | 启动时复位**真正残留**的；判定用「这次扫描什么时候开始的」，正在跑的绝不误清 |
| 播放会话永不结束 | 客户端异常退出，不会上报 Stopped | 心跳超过 10 分钟没更新就标记结束（结束时间用上次心跳） |
| HLS 转码目录 | 重启后注册表是空的，上一进程留下的分片再没人管（`/tmp` 是 tmpfs 时就是内存） | 启动时全清、此后只清「已停下且超过 5 分钟」的目录 |
| 字幕缓存 | 每个条目一份 VTT，只增不减 | 先删过期（默认 7 天），再按数量删最旧的（默认上限 2000 个） |
| 孤儿 ffmpeg | 父进程被 SIGTERM 时不会带走子进程 | 退出时统一终止在册的转码会话并清目录 |
| 播放进度/收藏的孤儿行 | `UserMediaData` 没有 ORM 级联，删条目不会带走它 | 扫描清理时显式一起删 |
| 限流桶 | 每个访问过的 IP 一个桶 | 超过 5000 个桶时清掉所有已过期的 |

播放会话（`emby_playback_sessions`）是这张表里唯一**故意保留历史**的：每播一次一行，
后台的「总播放次数 / 今日播放 / 一周热门 / 按日趋势」都靠它。默认不裁（历史统计口径不变）；
小机器想控制库体量可以设 `SESSION_RETENTION_DAYS=90`，看护线程会裁掉更早的**已结束**会话
（正在播的永远不碰），代价是统计只剩保留期内。

另外两件与「稳定」直接相关的事：

- **健康检查是常数级的**：`/api/health` 会报告转码会话数、正在扫描的库数、临时目录占用与磁盘余量；
  目录统计有硬上限（`REPORT_MAX_FILES`，默认 5000），残留再多也不会把探针拖慢，被截断时会标注
  `transcode_scan_truncated`。健康检查自身任何异常都只降级（返回空对象），不会变成 500。
- **删库与扫描互斥**：扫描中的库不允许删除（HTTP 409），删除改成分批（每批 500 条）——
  边扫边删会让已删除的库继续被插入条目，而 SQLite 会复用 rowid，新库撞上同一个 id 时那些
  条目会「复活」；分批则避免十万级库把面板拖死。扫描线程也会在批次边界发现库已删而提前收工。

可调环境变量：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `MAINTENANCE_INTERVAL` | `600` | 看护线程周期（秒），最低 60 |
| `SCAN_STALE_HOURS` | `6` | 超过这个时长还没结束的扫描才算「残留」 |
| `SESSION_STALE_MINUTES` | `10` | 心跳超过这个时长就当作会话已结束 |
| `SUB_CACHE_MAX_FILES` | `2000` | 字幕缓存文件数上限 |
| `SUB_CACHE_MAX_DAYS` | `7` | 字幕缓存天数上限 |
| `REPORT_MAX_FILES` | `5000` | 健康检查里目录统计的上限 |
| `SESSION_RETENTION_DAYS` | `0` | 播放会话保留天数（`0` = 永久保留）。设成如 `90` 会裁掉更早的已结束会话 |
